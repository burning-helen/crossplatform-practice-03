# Ответы на контрольные вопросы

## 1. Чем Electron отличается от нативной разработки и от Tauri? Каковы его сильные и слабые стороны?

Electron позволяет создавать настольные приложения на HTML, CSS
и JavaScript, используя встроенные Chromium и Node.js.

При нативной разработке приложение непосредственно использует
инструменты и библиотеки целевой платформы. При этом существуют
и переносимые библиотеки для разработки на компилируемых языках,
поэтому нативный исполняемый файл не обязательно означает
отдельную кодовую базу для каждой ОС.

Tauri также позволяет использовать веб-интерфейс, но отображает
его в системном WebView, а нативная часть обычно реализуется
на Rust.

Сильные стороны Electron:

- использование веб-технологий;
- общая прикладная кодовая база для настольных платформ;
- развитая экосистема;
- поставка определённой версии Chromium вместе с приложением.

Ограничения:

- большой базовый размер дистрибутива;
- накладные расходы браузерной инфраструктуры;
- необходимость регулярного обновления Electron и зависимостей;
- необходимость безопасно организовать доступ интерфейса
  к системным возможностям.

## 2. Что такое main process и renderer process? Сколько экземпляров каждого типа существует?

Главный процесс, main process, управляет жизненным циклом приложения,
создаёт окна, организует меню и выполняет привилегированные операции.

В одном экземпляре приложения Electron существует один главный
процесс. В нашем проекте его точкой входа является main.js.

Процессы отрисовки, renderer processes, отображают веб-интерфейс.
В базовой модели каждому окну BrowserWindow соответствует
отдельный процесс отрисовки. В сложном приложении Chromium
может создавать дополнительные процессы.

Поэтому Electron-приложение не обязательно состоит ровно
из двух процессов: кроме главного и процессов отрисовки
могут существовать процессы GPU, служебные процессы и другие.

## 3. Какую роль играет package.json? Какие поля нужны для упаковки?

package.json описывает проект: его название, версию, зависимости,
команды и точку входа.

В работе используются:

- name — имя пакета;
- version — версия приложения;
- description — описание;
- author — автор;
- main — файл главного процесса;
- scripts — команды запуска и сборки;
- devDependencies — зависимости разработки;
- build — настройки electron-builder.

Для подготовки дистрибутива должны быть корректно заполнены
метаданные name и version, задана существующая точка входа main.
Поля description и author требуются в рамках методички
и используются средствами упаковки.

В проекте main указывает на main.js, npm start запускает Electron,
а npm run dist формирует установщик Windows.

## 4. Почему в renderer отключён прямой доступ к Node.js? Что означают contextIsolation и nodeIntegration?

Интерфейс обрабатывает веб-содержимое. Если предоставить ему
полный доступ к Node.js, ошибка обработки недоверенных данных
или внедрение скрипта может привести к выполнению системных
операций с правами приложения.

nodeIntegration: false отключает предоставление Node.js
обычному коду страницы.

contextIsolation: true разделяет JavaScript-контексты страницы
и preload. Страница не получает прямого доступа к внутренним
объектам preload.

Эти настройки решают разные задачи и применяются совместно.
В работе дополнительно включена песочница sandbox: true.

Разрешённые операции предоставляются через ограниченный
API contextBridge. Наличие изоляции не отменяет проверку
аргументов и источников IPC-запросов.

## 5. Что такое preload и какова роль contextBridge.exposeInMainWorld?

Preload — скрипт, который выполняется перед загрузкой кода страницы
в процессе отрисовки. Он имеет доступ к разрешённым Electron API,
а при включённой песочнице — к ограниченному набору возможностей
среды Node.js.

contextBridge.exposeInMainWorld публикует выбранный API
из изолированного контекста preload в контекст страницы.

В работе опубликован объект window.api с методами:

- listDir — запрос содержимого рабочего каталога;
- onRefreshDirectory — подписка на команду обновления из меню.

Странице не передаются весь ipcRenderer и произвольные файловые
операции.

## 6. Как работают invoke/handle? Чем они отличаются от send/on?

ipcRenderer.invoke отправляет запрос из процесса отрисовки
и возвращает Promise.

ipcMain.handle регистрирует обработчик в главном процессе.
Возвращённое обработчиком значение становится результатом Promise.
Ошибка обработчика приводит к отклонению Promise.

В нашем приложении invoke/handle используются для чтения каталога:
интерфейс запрашивает данные и ожидает массив записей.

Пара ipcRenderer.send / ipcMain.on предназначена для событийного
обмена и не возвращает результат обработчика как Promise.
При необходимости ответ организуется отдельно.

Для передачи команды меню из main в renderer используется
webContents.send, а в preload сообщение принимается через
ipcRenderer.on.

## 7. Чем различаются win.loadFile и win.loadURL? Что используется в работе?

win.loadFile загружает локальный HTML-файл.

win.loadURL загружает содержимое по URL, например страницу
сервера разработки или удалённого сайта.

В работе используется loadFile с абсолютным путём к index.html,
сформированным через path.join(__dirname, 'index.html').

Интерфейс входит в состав приложения, поэтому для его загрузки
не требуется отдельный веб-сервер. Обращения к файловой системе
выполняются через IPC, а не напрямую из HTML-страницы.

## 8. Как обрабатывается жизненный цикл и почему macOS — особый случай?

app.whenReady() — метод, возвращающий Promise готовности Electron,
а не отдельное событие с таким именем. После его разрешения
создаются окно и меню.

Событие window-all-closed возникает после закрытия всех окон.
В проекте оно вызывает app.quit(), если платформа не является macOS.

На macOS закрытие последнего окна обычно не означает
завершение приложения. Поэтому приложение остаётся запущенным.

При событии activate проверяется количество открытых окон.
Если их нет, вызывается createWindow().

## 9. Как electron-builder создаёт дистрибутив? Почему не все сборки возможны на любой ОС?

electron-builder читает метаданные проекта и настройки build,
подготавливает Electron для выбранной платформы и архитектуры,
включает прикладные файлы и создаёт выбранный формат поставки.

В работе используется цель NSIS для Windows x64.
Результаты сохраняются в каталог dist.

Возможности межплатформенной сборки зависят от формата пакета,
системных инструментов, нативных зависимостей и требований подписи.

Например, подпись приложения macOS выполняется на macOS.
Поэтому наличие общей кодовой базы не означает возможность
подготовить любой подписанный дистрибутив на любой системе.

## 10. Почему дистрибутив Electron большой? Как можно уменьшить размер?

В дистрибутив включаются Chromium, Node.js и другие компоненты
среды Electron, а не только JavaScript, HTML и CSS приложения.

В нашей работе размер установщика составил
112 150 000 байт, что Windows отображает приблизительно как 106 МБ.

Для уменьшения размера можно:

- исключить ненужные файлы через настройки files;
- не включать отчёт, скриншоты и тестовые данные;
- оптимизировать изображения и другие ресурсы;
- удалять неиспользуемые зависимости;
- использовать подходящие параметры сжатия установщика;
- при необходимости проверить возможность исключения
  неиспользуемых локализаций.

ASAR объединяет файлы приложения в архив, но сам по себе
не является сжатием и не устраняет размер Chromium и Node.js.

Если минимальный размер является определяющим требованием,
следует рассмотреть другую архитектуру приложения.

## 11. Как чтение каталога связано с POSIX-совместимым программированием?

Приложение использует единый API fs.readdir, предоставляемый Node.js,
вместо отдельных реализаций перечисления файлов для Windows
и Unix-подобных систем.

Это иллюстрирует идею переносимого системного интерфейса:
прикладной код обращается к общей операции, а среда выполнения
организует её реализацию для целевой платформы.

Однако fs.readdir — API Node.js, а не прямое доказательство
POSIX-совместимости операционной системы. Windows от использования
этого метода не становится POSIX-совместимой.

Различия путей, прав доступа, регистра символов и файловых систем
могут сохраняться и требуют проверки.

## 12. Что возвращает process.versions и как это помогает диагностике?

process.versions — объект со строковыми версиями Node.js
и компонентов среды выполнения.

В Electron он содержит в том числе:

- process.versions.electron — версию Electron;
- process.versions.chrome — версию Chromium;
- process.versions.node — версию встроенного Node.js.

Эти данные помогают проверить доступность API, совместимость
нативных модулей и соответствие сообщения об ошибке
конкретной версии среды выполнения.

Версия из команды node --version относится к Node.js,
установленному в среде разработки. Она не обязана совпадать
с process.versions.node внутри запущенного Electron.

В приложении с изолированным интерфейсом нужные значения следует
передавать через ограниченный API preload или IPC, а не включать
полный доступ страницы к Node.js.
